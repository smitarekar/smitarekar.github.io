A RISC-V core, plus an instruction of my own

A single-cycle RV32I core in Verilog, with a custom multiply-accumulate added in the custom-0 opcode space. Dot products are most of inference math, and MACC does each step in one instruction instead of two.

ISA
RV32I plus MACC: rd = rd + rs1 × rs2 in one cycle
Checks
8 self-checking testbenches and a golden cross-check, all passing
Reference
A Python ISA model written from the spec, not from the RTL
riscv-core

The hard part

A processor can be nearly right for a long time. A core with a broken sign-extension path still runs most programs, and one that mis-decodes a rare immediate format passes every test that never uses it. So every module has its own self-checking testbench, the full core runs six hand-assembled programs, and MACC results are cross-checked against an independent Python model of the ISA.

MACC also needed a third register read. rd is both the accumulator and the destination, and a standard register file only has two read ports.

What testing caught

The bug wasn't in the RTL. My assembler encoded the halt pseudo-op, jal x0, 0, as an absolute address instead of a relative offset, so halt jumped back to address 0 and reran the program. Every existing test passed by luck, because a deterministic program recomputes the same values. The golden model expected a true self-loop, never saw one, and flagged it. That's the case for a second implementation in one example.

GPU compute, from both ends

In RTL, a soft GPU with a SIMT architecture that I'm building in Verilog. On real silicon, matrix multiply kernels tuned on an Apple M4 GPU, because the quickest way to understand a GPU is to watch it waste its own throughput.

metal-matmul

The hard part

A GPU gives you enormous throughput and almost no help using it. A kernel can run at a tenth of its capability and report no error, because nothing went wrong: the answer is right, it just took ten times longer. The arithmetic is identical in all three kernels here. What changes is how data moves between memory tiers.

Each kernel is checked against NumPy before a benchmark is allowed to run. Coalescing on top of tiling bought another 2.6% at 1024, which is inside run-to-run noise, and the README says so.

Why Metal

It was scoped as CUDA. My machine has no NVIDIA GPU, so the kernels are Metal. The memory-tier ideas carry over unchanged.

The SIMT GPU, in progress

The RTL side, built in four steps: a single-cycle scalar datapath, SIMT lane replication, branch divergence handled with active masks, and a tiled matrix multiply kernel to run on it.

systolic-mm-accelerator

Sixteen processing elements each hold one weight and do one multiply-add. Activations stream west to east while partial sums accumulate north to south, in Q8.8 fixed point, over AXI4-Stream.

The hard part

A systolic array is a machine built out of timing. None of the PEs knows anything about the matrix being computed, so correctness comes entirely from data arriving at the right PE on the right cycle. The failure to fear isn't a wrong multiply. It's a value arriving one cycle early.

Running a real network

A small CNN trained in PyTorch, with its final classifier layer quantized to the array's exact Q8.8 format and mapped onto the hardware as three 4 × 4 weight tiles. Quantization changed none of the model's decisions, and the float model scores 98.5% on the full 10,000-image test set.

axi4-crossbar

The hard part

An interconnect has no interesting arithmetic. Every bug in it is a timing or ownership bug, and they all fail the same way: a transaction that never completes, on a bus where nothing times out.

What testing caught

Same-cycle completion. A fresh grant, AW and W can all resolve on one clock edge. The first arbiter's FSM only read its pre-edge state, so it couldn't see a completion its own forwarding had just caused, and the transaction looked like it hung forever. The plain-Verilog suite found that one; UVM found others.

Measured, not assumed

The back-to-back gap between two uncontested writes is measured in simulation, 20 ns, rather than asserted from a number typed by hand.

pcie-tl-dl

The hard part

PCIe is a spec most people implement from memory of a diagram, and that's where the bugs come from. CRC seeds, bit orderings, and header bits that routing elements may legally rewrite are all easy to assume by analogy and wrong to assume without checking.

What's still open

All six build phases are done. Two details, the LCRC wire byte order and the DLLP CRC-16 polynomial, are self-consistent for this design's own loopback but not yet checked against the PCI-SIG spec text, and five open items are listed in the README for sign-off.

uart-asic-flow

The RTL

A baud generator, a transmitter, a 16× oversampled receiver with glitch-checked start-bit detection, and four memory-mapped registers, so a CPU on an APB bus can send and receive serial bytes. 4 of 4 testbenches, 29 checks.

The verification

A real UVM component hierarchy without a commercial simulator: cocotb and pyuvm on Icarus Verilog. The scoreboard checks against an independently decoded serial stream, because a loopback can't tell you a byte is right when both halves of the trip run through the same design. The DUT is a pinned git submodule, so testbench and design version independently.

What testing caught

My own driver. It signalled done as soon as the TXDATA write finished instead of when the byte finished shifting out, so the baud-sweep test changed BAUDDIV mid-frame, which the DUT's README says never to do. The monitor decoded the first two or three bits of a frame correctly and then drifted into garbage.

The layout

OpenLane on Sky130 HD: synthesis, floorplan, placement, clock tree, routing and signoff in one pass. 530 cells synthesized, 1,767 placed with fill, 0.0176 mm² of die at 42.6% utilization. The one finding was five max-fanout guideline violations on clock buffers, and timing still closed.

A Kalman filter, from Python to fixed-point RTL

An Extended Kalman Filter that tracks a 2D target from noisy range-bearing radar measurements. Written first in float64 Python, then ported to fixed-point Verilog and checked against the Python at every step, not just the last.

Error
6.462 m RMSE in fixed point against 5.947 m in float64
Format
Q11.14 datapath, Q15.14 for S, det(S) and its inverse
Match
60 of 60 steps within tolerance, CORDIC for the trig
ekf-target-tracker

The hard part

A Kalman filter is a feedback loop over a covariance matrix. A small rounding error in P this step becomes a slightly wrong gain next step, which makes a slightly wrong state, which makes a worse P. In floating point that loop is stable. In fixed point it isn't guaranteed to be.

Range noise and bearing noise here live about 5.7 orders of magnitude apart, so the inverse of S legitimately reaches about 9,133. Q11.14 tops out at ±2,048, which is why S gets a wider format than the rest of the datapath.

Where I've used it before

The Borosil data logger ran an EKF in its DSP pipeline to hold ±0.03 °C RTD accuracy. This project does the same math with the floats taken away.
